## 产品定位

从青凝已有实践中提炼应用与 Agent 的通用接入规范及其开源参考实现，让不同应用以一致的方式向 Agent 提供任务、上下文和获准方法，并取得消息、调用请求、执行状态与结果。

首版以本机 Agent 接入为实际交付范围。通用约定不绑定论文、笔记、学习任务等业务对象；个人应用只是优先切入场景，不是协议的领域限制。参考实现承接现有运行能力，不能仅发布字段说明便视为可使用的开源项目。

接入者可以在创建应用时引入，也可以为已有应用补充接入。使用者可以在应用中发起任务，也可以在原有 Agent 宿主中发起任务；两种入口都通过获准的数据与方法完成工作。

产品连接的完整路径是：

> 应用或原有 Agent 中的任务 → 获准使用的上下文 → 用户选择的 Agent → 应用允许的操作 → 结果保存或展示 → 用户继续使用。

对话是发起和澄清任务的一种入口。任务也可以从原有业务页面的按钮、材料选择或操作菜单发起。通用约定同时允许纯对话、只读分析、内容生成和带业务操作的任务；结果是否需要保存，取决于应用明确提供的能力和用户目标。

## 现有实践与通用化目标

当前青凝已有引擎与会话适配、MCP 工具桥、受限方法目录、业务授权和执行回执等实践。提炼应从这些真实调用边界出发，区分共同语义、青凝业务绑定和跨适配器差异。

源码基线、精确位置和历史差异集中记录在 [参考实现设计的来源附录](sdk-and-qingning-integration-design.md#15-2026-11-02-历史来源基线)及其当前来源核查中；源码核查不等于本轮重新完成了部署或真实模型运行验收。现有能力也不因尚未独立开源而被重新标为没有实现。

### 与 ACP 和 MCP 的关系

ACP 主要承载应用与 Agent 的会话交互；应用还可以把自身 MCP 服务配置交给 Agent。MCP 主要规范 AI 应用与资源、工具等能力的交换。两者可以配合使用，不能笼统视为二选一的同层替代品。依据：[ACP 架构](https://agentclientprotocol.com/get-started/architecture)、[MCP 规范](https://modelcontextprotocol.io/specification/2026-07-28)。

通用接入规范应优先复用已有标准和现有实现，明确必要的能力配置与映射；目前不预设需要再发明一套网络消息协议。若应用通过 MCP 将整个 Agent 暴露成可调用工具，需要另行明确该封装如何表示会话、进展、取消与结果，不能把封装语义当作 MCP 自动提供的完整 Agent 接入行为。

“交给模型的方法”应区分方法描述、调用请求和实际执行。应用提供方法说明及参数、结果约束；Agent 返回调用请求和参数；实际执行方校验授权后运行并返回回执。生成的代码或函数文本属于产出，不自动获得执行权限。对外接入约定面向 Agent 运行时，由运行时处理具体模型交互。

## 参与角色与使用场景

下列情况用于说明谁负责接入、谁使用和谁维护，不代表三套不同场景协议。应用开发者与最终使用者处在同一条使用链路中；个人应用创建者往往同时承担两种角色。所有情况共用同一通用接入约定，新项目与已有项目只是在接入时机和现有接口条件上不同。

| 参与情况 | 典型处境与诉求 | 怎样使用本项目 | 最终取得的结果 |
| --- | --- | --- | --- |
| 个人应用创建者，建议优先服务 | 用 AI 或自己编程创建个人应用，已有 Agent，希望将两者连接 | 自己或让 AI 编码工具接入 A、B 所需能力；随后从应用或原宿主授权并发起任务 | 自己创建的应用可与 Agent 协作，产出交付相应入口，业务成果回到应用 |
| 应用开发者与维护者 | 创建应用给别人使用，或维护已有应用，希望支持用户自己的 Agent | 声明共同数据与方法；A 接通应用会话与界面，B 提供应用能力出口，再交付更新 | 使用者可从相应入口连接，开发者复用已有适配而无需为每个角色定义协议 |
| 最终应用使用者 | 使用别人提供的应用，希望 Agent 处理材料或执行获准操作，不负责开发 | A 在应用内连接 Agent；B 在原宿主中连接应用服务；确认权限、提出任务并查看成果 | 在所选入口完成任务，不需要修改源码或理解接入协议 |

个人应用创建者同时是接入者和最终用户，是建议的第一批试用对象。是否熟练编程不是划分条件；只会借助 AI 创建应用的人，也应能通过清楚的接入说明让编码工具协助完成。

应用开发者与维护者包含独立开发者、开源项目维护者，以及有足够扩展接口的应用插件作者。技术能力不改变应用必须提供上下文、业务操作和结果回读入口的要求。

最终用户通常从应用提供的“连接我的 Agent”入口，或应用提供的 MCP 连接说明开始，不需要先理解开发者接入包。

### 扩展用户与接入渠道

应用模板、脚手架和 AI 应用生成工具的维护者，可以在后续将本项目接入方式预置到模板中，让生成的本地应用更容易获得同样能力。这是潜在的扩展用户与分发渠道，尚不构成已确认的首版平台集成需求。

AI 编码工具本身是辅助接入的执行工具；产品的需求、授权和验收仍由创建者或开发者负责。

### 接入者与使用者的关系

开发者使用本项目完成应用接入；最终用户从应用或原有 Agent 中使用已接入能力。个人创建者可以一人完成这两段工作，但产品不能因此省略相应连接、授权、状态说明和恢复流程。

“应用已完成接入”与“这位用户已完成相应连接和授权”是两个不同前提。前者由应用作者完成，后者由最终用户完成。只安装本机连接器，不能让一个尚未接入的封闭应用自动获得业务操作能力。

## 核心问题与价值

用户已有应用，也已有自己的 Agent，但两者之间缺少稳定的任务、上下文、操作和结果连接。

产品提供三个直接价值：

1. 应用创建者可以复用接入方式，不必分别理解和维护每种 Agent 的全部调用差异。
2. 使用者可以选择已有的 Agent 环境及其受支持配置，不必为每个应用重新搭建一套工作环境。
3. 产出交付发起任务的界面；需要业务操作时，成果进入应用原有数据和功能，供用户继续使用。

第一批用户是否愿意安装、配置并持续使用该能力，仍需通过真实试用验证。不能把技术可实现直接等同于市场需求已成立。

## 两种使用场景

| 场景 | 用户在哪里提出任务 | 接入方做什么 | 使用方怎么用 |
| --- | --- | --- | --- |
| A 在应用中调用自己的 Agent | 原应用的业务页面或对话区 | 接通 Agent 会话，提供上下文与获准方法，展示消息和结果 | 在应用内连接 Agent、确认范围、发起任务并使用成果 |
| B 在原有 Agent 中操作应用 | 用户原本使用的 Agent 宿主 | 将应用能力通过 MCP 开放，保留原业务权限和数据 owner | 将应用服务连接到 Agent，在原宿主提任务，成果通过应用原有功能可见 |

### 场景 A 在应用中调用自己的 Agent

例子：研究者用 AI 创建或改造本地文献库，希望直接在文献库里整理资料。

接入方让 AI 编码工具或开发者按同一规范接通材料读取、笔记保存、Agent 会话与必要界面。会话交互优先复用 ACP 或原生适配，应用方法可经 MCP 或受控工具桥提供。

使用者在应用内选择 Agent、授权材料与操作，提出“比较这些材料并整理笔记”，处理必要补充或批准，再打开成果。应用负责本应用会话的展示与控制，原生历史仍由 Agent 引擎持有。

创建者自用时独自完成接入与使用；交付给别人时，开发者完成接入，每位使用者连接各自的 Agent。两种情况不需要不同协议。

### 场景 B 在原有 Agent 中操作应用

例子：用户习惯在已有 Agent 中安排工作，希望直接说“从我的资料库读取最近材料，整理笔记并保存回去”。

接入方将资料库的查询、读取、保存等获准能力通过 MCP 开放，提供连接与授权说明。使用者在自己的 Agent 宿主中连接该服务，确认权限后发起任务。

Agent 调用应用能力，应用进行业务校验、实际执行并返回结果。用户在原宿主继续对话，也可打开应用查看成果。应用不必另建聊天窗口，也不默认取得原宿主的完整会话或控制整个 Agent。

该场景与“把整个 Agent 包装为一个 MCP 工具让应用调用”不同；后者不是本轮必选的第三条执行路径。

### 场景之外的接入条件

新项目在创建时预留入口，已有项目复用现有数据和方法补接；这两种接入时机都可服务 A、B。给自己用、分享给别人用、多个应用共用本机环境，也不改变共同数据与方法约定。

每个应用分别取得授权，不能因复用了一个 Agent 环境便默认共享全部记忆、文件和业务权限。B 的原宿主还负责跨服务上下文聚合与披露：连接多个应用不等于允许互传材料，发往其他应用的参数需符合用户已授权的目的、范围和接收方。工具描述或结果不能扩大许可；宿主不能落实时，明确不提供该隐私隔离承诺。

最终用户不负责修改源码、定义工具或复制认证令牌；无代码使用的前提是应用作者已经完成接入。写入能力还需满足协议规定的重复执行准入；缺少保障时，记录为该写入目标未闭环，不以只读演示替代。

模板和应用生成工具的预置集成可以作为后续分发方向。个人创建者仍是建议的首批试用对象，但这只是切入建议，不改变两种入口共同覆盖的目标。

## 复用自己的 Agent 的含义

| 层次 | 产品含义 | 边界 |
| --- | --- | --- |
| 运行能力 | 使用用户选择的本机 Agent 执行任务，沿其受支持的认证、模型与执行机制工作 | 不统一承诺所有厂商的订阅额度都能被第三方应用复用 |
| 个性化配置 | A 用户明确选择加载支持的配置；B 继续由原宿主管理个人配置 | 显示适用来源和范围，不因接入应用自动导入全部工具、hooks、凭证与文件权限 |
| 应用会话延续 | A 的应用任务持续对话，支持时恢复；B 在原有宿主中继续 | A 默认建立应用范围会话；B 不要求另建应用对话，原生历史仍归引擎 |
| 已有个人会话接入 | A 需引擎支持并明确授权才能接入指定历史；B 用户本来就在原宿主对话 | A 不默认接管桌面会话；B 不让应用读取全部原会话，均不承诺跨引擎交换历史 |

复用个性化配置不能绕过应用权限。个人 skills、工具或脚本若会访问更多目录、网络或服务，必须纳入实际权限判断。

Agent 在本机运行也不等于模型推理完全离线。连接与任务界面要让用户理解所选 Agent 的数据处理方式，包含材料是否会提交给外部模型服务。

## 产品职责边界

| 负责方 | 负责的事情 |
| --- | --- |
| 本项目 | 提炼共同数据与方法约定；A 适配应用范围内的 Agent 连接与会话，B 适配应用能力出口；沿实际能力支持事件、批准、恢复与断开 |
| 接入应用 | 用户身份、业务规则、上下文选择、业务工具的授权校验、数据写入与读回、业务结果展示 |
| 原生 Agent | 自身的推理和工具执行循环、受支持的认证机制、原生会话历史，以及它实际提供的执行限制 |
| 最终用户 | 选择 Agent，授予明确范围的权限，提供任务，处理需要人工决定的操作 |

应用数据继续由应用已有的业务接口和存储负责。本项目不成为第二套业务数据库或任务权限系统；原生会话历史也不复制成另一套权威存储。

应用工具权限与 Agent 原生执行权限是不同边界。A 需落实其管理的文件、终端、网络和工具限制，不能通过其他路径绕过授权。B 的原生权限由原宿主与用户管理，应用服务只能保证自身资源、方法和撤权边界；不能把 MCP 授权宣称为全机沙箱。必要安全承诺做不到时明确不支持，不隐性扩大权限。

## 首版范围建议

- 聚焦用户自己电脑上运行的应用，以及该电脑上的 Agent。
- 同时定义 A 应用内发起和 B 原有 Agent 中发起两种入口，共用应用数据、方法、授权与结果语义；不要求 B 复制 A 的聊天界面和会话控制。
- 首批目标接入对象为 Codex、Claude Code 和 DeepSeek Harness；具体正式支持范围由逐引擎的兼容与完整流程验收决定。
- A 允许应用接入多个 Agent 环境，每个会话选择一个执行者；B 由用户在已有宿主中选择 Agent。
- 支持用户主动发起任务、应用提供上下文、调用获准业务工具，以及结果展示和保存。
- A 支持明确选择的个性化配置与应用范围内的持续会话；B 的个人配置和原对话仍由原宿主管理。
- 新项目和已有项目遵守同一套连接、授权、任务与结果规则。

自动多 Agent 组队、跨电脑调度、云端网站调用用户电脑、远程多用户运行、通用定时执行，以及封闭软件的零修改控制，暂不作为首版目标。

已有应用需要可修改源码、插件入口或足以完成目标能力的扩展接口。纯对话或只读分析可以是完整接入目标；如果应用承诺保存或修改业务数据，则必须接通对应执行与结果回读，不能用显示回答代替该目标完成。

## 首个代表场景

个人知识库可使用同一套数据和方法覆盖两种入口：

1. 用户选择几篇已经收录的论文。
2. 提出“比较研究方法，整理成阅读笔记”的任务。
3. Agent 读取获准材料，必要时追问。
4. 用户查看产出，并授权保存到指定笔记位置。
5. 应用通过原有接口保存，读回笔记并展示。
6. 用户关闭再打开应用，仍能找到笔记；在受支持条件下继续原会话追问。

以上为 A。B 从用户原有 Agent 发起同样目标，通过资料库的 MCP 能力读取并保存，原宿主负责对话，资料库负责业务成果。两种入口都要验证原业务权限和结果，不能因某条路径成功便宣称另一条也已验收。

知识库只是例子。完整功能与异常流程见 [首版核心功能与完整使用流程](v1-features-and-flows.md)，数据与方法约定及标准复用见 [通用接入协议草案](general-integration-contract.md)。
