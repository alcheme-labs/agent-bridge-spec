# ServerAgent 对 Local Agent Bridge 的接入期望

日期：2026-11-13。状态：消费者期望清单，待 Bridge 项目评审；不修改双方协议，不构成选型或开发授权。

## 目的与核对基线

希望 Bridge 承接维护 Agent 的运行接入，让 ServerAgent 继续负责维护委托、服务承诺、候选验证、启用及真实结果。期望应能复用于其他应用，不要求 Bridge 内置 ServerAgent 的领域对象、维护状态机或业务知识。

核对依据是 Bridge 当前 [SPEC draft 0.1](../SPEC.md)、[通用接入约定](general-integration-contract.md)和[SDK 技术设计](sdk-and-qingning-integration-design.md)，以及 ServerAgent 的[维护边界](../../ServerAgent/CAPABILITY-PROTOCOL.md#agent-boundary)与[维护上下文](../../ServerAgent/CAPABILITY-PROTOCOL.md#maintenance-context)。这些跨项目链接仅用于本机对照，不构成运行时目录依赖。

Bridge 目前尚无公共实现、可安装包或正式兼容矩阵。必须区分：**规范尚待细化、规范已有但待实现/验收、具体消费者接入尚未闭合。** 下列清单不把“尚未交付”一概记为“协议没有考虑”。

下文“已有”指草案已有约定，不表示公共实现已交付，也不否认青凝已有的来源实践。四项期望的重要性针对 ServerAgent 的接入需要，不要求 Bridge 的每个引擎、运行方式或首发版本全部具备；实际支持范围须明确声明，已有必需安全规则不能因此省略。

ServerAgent 当前生成路径已经从获准上下文产生结构化候选，并由宿主检查、保存与启用；接入 Bridge 不能要求先开放更多工具、迁移维护状态或改写服务契约。

## 希望优先明确的四项

| 期望 | 对 ServerAgent 的重要性 | Bridge 已有基础与实际缺口 | 希望补清楚的边界 |
| --- | --- | --- | --- |
| 1. 明确后台受托任务的运行方式 | 自维护所需的一种运行组合，不取消人工交互方式 | SPEC §6–7 和 SDK §4–5 文档已有可信运行策略、批准与补充信息交互，也考虑后台入口；尚未完整说明后台服务主体怎样凭现有有效委托发起任务，以及无人答复时怎样处理。 | 区分真实执行主体、授权来源与接收者。在有效委托范围内、且引擎支持相应授权策略时，可由可信宿主按策略自动处理，不要求每次真人在线；这不等于伪造一次人工点击。未被委托覆盖、要求当次人工决定或缺少必要信息时，按宿主策略明确等待、超时或拒绝，不默认同意或无限等待。委托判断仍由宿主负责，Bridge 不新建授权中心。 |
| 2. 明确模型结构化候选的接入方式 | 当前候选生成路径所必需 | SPEC §7、通用约定 §3/5 已约定应用声明的候选 schema，并区别于工具回执；SDK 的主入口还未把生成约束如何传入、逐引擎协商和完整返回写清楚。 | 说明如何传递应用的产出要求及声明逐引擎支持。可以使用原生结构化输出约束，或在双方认可的模式下由宿主解析完整文本中的结构化数据并校验；不能把任意文本或原生轮次完成当成候选通过。Bridge 保真交付实际输出并说明完整性/限制，宿主负责 schema 与业务正确性检查；无效、截断或不可用时不启用。模型候选与 MCP 工具执行回执分别消费，不要求 Bridge 判断服务业务是否正确，也不新增专用候选协议。 |
| 3. 明确主任务的时限、停止与预算能力 | 有界维护运行所必需；具体预算维度按支持声明 | SDK §3/5 文档已有取消、真实用量及停止状态；§6 对辅助调用明确了 AbortSignal 和超时，但主任务尚未明确相应时限/预算的输入与执行边界。 | 由可信宿主提供所需时限、停止信号及运行限制；分别声明引擎可强制的限制、宿主能发出的停止请求、实际观测值和未知信息。不能把观测用量当硬上限，也不承诺所有引擎都支持精确费用/token 封顶。若某项硬限制是本次任务的必要条件而所选组合无法落实，应明确不支持该组合，不能暗中降成软限制。停止请求与已停止分开；整体维护次数、重试预算和调度仍归 ServerAgent。 |
| 4. 给非 Node 宿主一条可消费路径 | 实际采用的重要条件 | SDK §1/11 当前设计为 Node 参考实现；ServerAgent 是 Python，尚无经验证的非 Node 消费路径。属于接入可达性缺口，不是缺少通用业务语义。 | 说明非 Node 宿主如何复用同一接入能力，以及需承担哪些进程、认证、交互和部署成本。可以利用已有受支持绑定，不要求立即提供 Python SDK、新网络协议或独立 daemon；也不应要求 ServerAgent 迁移语言、复制引擎驱动或接入青凝账号体系。 |

这些是待 Bridge 确认的消费者要求，不是其已经承诺的接口字段或首发范围。第 2 项尤其不能误报为“目前没有结构化候选约定”；缺的是具体接法与逐组合证据。

## 已经有约定，但接入时必须兑现

以下属于已有规则的实现与消费者验收要求，不另列成四项之外的新协议功能。

- **可信范围、隔离和撤权。** SPEC §5/10、SDK §4 已要求可信运行绑定和执行/交付重验。需要在同一应用下的不同服务实例及不同维护委托中落实：不能串用上下文或权限，也不能仅因接入就将未获准披露的外部 Agent 历史交给服务；获准且必要的材料仍可使用。当前无工具、受限候选生成方式应有可声明和核验的运行组合，不代表未来维护永远不能使用授权工具。不为兼容放宽原生文件、终端或网络边界；不支持所需约束的组合明确不支持。
- **关联关系与职责不丢失。** 宿主能将会话/轮次、候选产出及真实工具结果对应到自己的维护操作；会话 ID 不冒充授权或业务幂等键。服务身份、基线实现版本、候选有效性、并发启用检查仍由 ServerAgent 判断。Bridge 可以按自身约定保留运行句柄、会话映射和必要恢复信息，但不成为服务活动版本、维护操作业务状态或权限的第二权威。
- **失联与重启保持真实语义。** SDK §3/4/10 已区分原生恢复失败、未知效果和保存指针失败，禁止静默新建或盲重投。需要证明宿主能先查询原维护结果，再按真实状态决定接续、重新组织上下文或停止；不要求原生会话永远可恢复，也不让 Bridge 接管业务恢复。已启用的候选不能因完成事件丢失而再启用一次。
- **能力和成果可以核实。** SPEC §9 已要求逐组合兼容声明，SDK 已区分轮次完成与业务完成。实际交付需提供所支持引擎/版本/运行方式的证据，区分声明、源码检查与真实流程通过；不能只写“支持 ACP/MCP”或以 Agent 的“完成”文本宣称服务修复成功。

## 最小可消费范围与责任边界

最先有价值的范围是：**宿主凭有效维护委托提供获准上下文和产出约束，在满足所需运行限制的组合中发起候选生成；Bridge 保真返回实际产出、完整性和执行状态，ServerAgent 只对通过原有验证的候选决定启用。** 生成可以失败、中断或没有可用候选，不承诺每次都在时限内生成正确实现，也不把部分输出或未知结果当成功。

这个范围只描述当前原型最先消费的接入方式，不把 ServerAgent 的长期维护能力限定为无工具生成；工具自主调查、远端接入、多 Agent 编排或个人会话复用按后续实际需求另行协商。

这是用于讨论接入是否足够的范围，不是本次实施计划。之后若验证，应沿用真实服务维护任务，检查接入是否保持原有权限、候选验证、恢复和调用方结果；本次没有运行这条验证，也不宣称能节省多少 token 或人工工时。

Bridge 不需要负责服务契约、业务真值、独立验收、候选发布、定期巡检、业务状态库或整个维护队列。它也不必为 ServerAgent 增加专用 schema、工具注册平台或全局知识库。若这些已有责任被搬入 Bridge，或需要并行维护两套状态与执行路径，就增加了接入成本并模糊了边界。

本清单仅保存 ServerAgent 消费者视角的期望，尚未直接发送到其他会话；不修改 Bridge 或 ServerAgent 的协议正文、实现及其他项目。
